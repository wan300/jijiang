# 06 - 核心业务流程

> 本文聚焦"会跑起来"的关键业务链路：状态机、时序图、延迟调度、异常路径。  
> 所有流程图使用 Mermaid 语法，GitHub / 各大 IDE 默认支持渲染。

## 1. 概览

| 流程 | 涉及模块 | 关键风险 |
| :--- | :--- | :--- |
| 1. 微信登录 | user | Token 时效、session_key 泄漏 |
| 2. 实名认证 | user, risk | OCR 置信度、人工审核队列积压 |
| 3. 讲师入驻 | user, payment | 保证金支付、资格复核 |
| 4. 服务发布 | service, risk | "先发后审" 失控、违规内容 |

| 6. 订单履约 | order, message | 超时推进、凭证完整性 |
| 7. 退款与仲裁 | order, payment, admin | 协商争议、多次退款 |
| 8. 评价与信誉 | review, user | 恶意差评、信誉炒作 |
| 9. 资金结算 | payment | T+1、对账差异 |

## 3. 延迟队列与超时调度

### 3.1 Redis ZSet 延迟队列设计

```text
┌──────────────────────────────────────────────────────────┐
│  Redis ZSet 键名约定（按业务场景分离）                   │
├──────────────────────────────────────────────────────────┤
│  delay:order:pay:timeout         —— 15min 支付超时        │
│  delay:order:accept:timeout      —— 24h 接单超时          │
│  delay:order:auto-confirm        —— 7d 验收自动确认       │
│  delay:seller:settle             —— 24h 冻结转可用        │
│  delay:dispute:evidence          —— 48h 举证超时          │
└──────────────────────────────────────────────────────────┘

成员（member）：orderId 或 "orderId:bizKey"（便于幂等）
分值（score）：到期时间戳（毫秒）
```

### 3.2 扫描与消费

```text
┌─────────────────────────────────────────────────────────┐
│  @Scheduled(fixedDelay = 30_000)                        │
│  public void scan() {                                   │
│      Set<String> ready = delayQueue.pop(queue, 100);    │
│      for (id : ready) {                                 │
│          try { handler.handle(id); }                    │
│          catch (Exception e) {                          │
│              // 失败重试：重新 push 延迟 1 分钟            │
│              delayQueue.push(queue, id, Duration.ofMinutes(1)); │
│          }                                              │
│      }                                                  │
│  }                                                      │
└─────────────────────────────────────────────────────────┘
```

### 3.3 兜底：数据库扫描

Redis 宕机或任务丢失时，由定时任务扫描数据库兜底：

```sql
SELECT id FROM order_main
WHERE expire_time < NOW()
  AND status IN (10, 20, 40)
LIMIT 500;
```

执行周期：每 5 分钟一次。对命中订单执行与 Redis 消费相同的业务逻辑，保证最终一致。

## 4. 流程一：微信登录

```mermaid
sequenceDiagram
    participant WX as 微信小程序
    participant BE as 后端
    participant WXP as 微信开放平台
    participant DB as MySQL
    participant R as Redis

    WX->>WX: wx.login() 获取 code
    WX->>BE: POST /api/auth/wx-login {code}
    BE->>WXP: jscode2session(appid, secret, code)
    WXP-->>BE: {openid, session_key, unionid}
    BE->>DB: SELECT * FROM user WHERE openid=?
    alt 用户存在
        BE->>DB: UPDATE last_login_time
    else 用户不存在
        BE->>DB: INSERT user(openid, nickname默认, current_role=1)
    end
    BE->>BE: 生成 JWT access(2h) + refresh(7d)
    BE->>R: SET refresh:{uid} {token} EX 604800
    BE-->>WX: {accessToken, refreshToken, userInfo}
    WX->>WX: uni.setStorageSync('token',...)
```

**异常处理**：

| 异常 | 处理 |
| :--- | :--- |
| `jscode2session` 40029 (code 无效) | 提示"登录已失效，请重试"；前端重新 `wx.login` |
| 微信接口超时（3s） | 返回 `90001`；前端重试 1 次 |
| 用户状态被封禁 | 返回 `10003`；前端引导至客服页 |

## 5. 流程二：实名认证

```mermaid
sequenceDiagram
    participant FE as 小程序
    participant BE as 后端
    participant OSS as 私有 OSS
    participant OCR as 百度 OCR
    participant DB as MySQL
    participant WX as 微信订阅消息

    FE->>BE: GET /api/upload/oss-token?scene=verify
    BE-->>FE: 私有 STS 凭证
    FE->>OSS: 上传学生证 -> 返回 url
    FE->>BE: POST /api/user/verify/submit {imageUrl, campusId, realName, studentNo}
    BE->>BE: 校验 Redis verify_limit:{uid} 60s
    BE->>DB: INSERT verify_record status=1
    BE->>DB: UPDATE user.verify_status=1
    BE->>OCR: recognize(imageUrl)
    OCR-->>BE: {name, studentNo, school, confidence}
    alt confidence >= 0.85 且学校匹配 且 name/no 一致
        BE->>DB: UPDATE verify_record status=2, review_mode=auto
        BE->>DB: UPDATE user.verify_status=2
        BE->>WX: 推送"认证通过"
    else 置信度低/不匹配
        BE->>DB: 保持 status=1 进入人工队列
        Note over BE: 运营端看到待审列表，手动通过/驳回
    end
    BE-->>FE: {recordId, status, message}
```

**人工审核**：运营同学在管理后台按记录逐条审核，点击"通过/驳回"。

## 7. 流程四：服务发布（先发后审）

```mermaid
flowchart TD
    A[讲师填写服务] --> B[POST /api/service/publish]
    B --> C{敏感词初筛}
    C -- 命中高危词 --> D[拒绝上架<br/>返回提示]
    C -- 通过 --> E[写库 status=ON_SHELF]
    E --> F[立即展示到搜索/分类]
    F --> G[异步 AI 内容安全检测]
    G --> H{是否违规}
    H -- 否 --> I[保持上架]
    H -- 是 --> J[自动下架<br/>冻结讲师提现<br/>通知运营]
    I --> K[人工巡检 定期抽查]
    K --> H
```

**核心 SOP**：

1. 前端提交前先本地过滤"微信/手机号/代写/保过"等关键词
2. 后端 DFA 过滤二次拦截
3. 上架成功后异步调用内容安全 API
4. 违规商品自动下架，并在 `risk_log` 记录，累计 3 次封号

## 8. 流程五：下单支付（核心路径）

```mermaid
sequenceDiagram
    participant FE as 小程序
    participant BE as A后端
    participant PS as B支付服务
    participant DB as MySQL
    participant R as Redis
    participant XHP as 虎皮椒

    FE->>BE: POST /api/order/preview
    BE-->>FE: 价格明细
    FE->>BE: POST /api/order/create (idempotencyKey)
    BE->>R: SETNX idempotency:{key} EX 300
    alt 键已存在
        BE-->>FE: 返回已有订单（防重复提交）
    else
        BE->>DB: BEGIN
        BE->>DB: UPDATE service_item SET used_stock=used_stock+1 WHERE id=? AND stock>used_stock
        alt 行锁未命中（库存不足）
            BE->>DB: ROLLBACK
            BE-->>FE: 20005 库存不足
        else
            BE->>DB: INSERT order_main status=10, expire_time=NOW()+15min
            BE->>DB: INSERT order_log (10)
            BE->>DB: COMMIT
            BE->>R: ZADD delay:order:pay:timeout orderId score=now+15min
            BE-->>FE: {orderId, orderNo}
        end
    end

    FE->>BE: POST /api/payment/create
    BE->>DB: SELECT order WHERE status=10
    BE->>PS: POST /internal/payment/orders (HMAC)
    PS->>XHP: POST /payment/do.html
    XHP-->>PS: payUrl / qrCodeUrl
    PS->>DB: INSERT payment_order status=1
    PS-->>BE: payUrl / qrCodeUrl
    BE->>DB: INSERT payment_record 摘要 status=1
    BE-->>FE: 收银台/二维码

    FE->>XHP: 打开收银台或扫码支付
    XHP-->>FE: 支付结果提示

    XHP->>PS: POST /api/payment/xunhu-notify (异步)
    PS->>PS: 虎皮椒验签 + appid + 金额校验
    PS->>DB: UPDATE payment_order status=2, transaction_id
    PS->>BE: POST /internal/payment/callback (HMAC)
    BE->>BE: HMAC + timestamp + nonce 校验
    BE->>DB: SELECT payment_record WHERE out_trade_no=?
    alt 已处理
        BE-->>PS: success
    else
        BE->>DB: BEGIN
        BE->>DB: UPDATE payment_record status=2, transaction_id
        BE->>DB: UPDATE order_main status=20, pay_time, expire_time=NOW()+24h (WHERE status=10)
        BE->>DB: INSERT order_log (10->20)
        BE->>DB: COMMIT
        BE->>R: ZADD delay:order:accept:timeout orderId score=now+24h
        BE->>FE: 推送订阅消息"支付成功"
        BE-->>PS: success
    end
```

**关键保障**：

1. **幂等键**：客户端提交 `X-Idempotency-Key`（UUID），后端 Redis `SETNX` 存储 5 分钟，防重复提交
2. **库存扣减**：UPDATE 必须带 `WHERE stock > used_stock`，利用 InnoDB 行锁
3. **回调幂等**：B 的 `payment_order.trade_order_id` 与 A 的 `payment_record.out_trade_no` 均唯一，状态前置校验
4. **超时控制**：支付超时 15 分钟（释放库存）；接单超时 24 小时
5. **内部签名**：A/B 内部接口使用 `X-JJ-*` HMAC-SHA256，Redis nonce 防重放

## 10. 流程七：退款与仲裁

### 10.1 退款类型

| 类型 | 触发 | 金额 | 备注 |
| :--- | :--- | :--- | :--- |
| 支付超时退款 | 15 分钟未支付 | 全额 | 自动，无需审核 |
| 接单超时退款 | 24 小时未接单 | 全额 | 自动，无需审核 |
| 买家协商退款 | 双方在订单内协商 | 部分/全额 | 无需平台介入 |
| 仲裁退款 | 买家申请，平台判定 | 平台决定 | 3 人仲裁团 |
| 管理员退款 | 违规/异常 | 全额 | 需操作审计 |

### 10.2 仲裁流程

```mermaid
sequenceDiagram
    participant B as 买家
    participant S as 卖家
    participant BE as 后端
    participant AD as 管理后台
    participant PS as B支付服务

    B->>BE: POST /api/order/refund/apply (expectAmount, reason, 证据)
    BE->>DB: UPDATE order.status=70
    BE->>DB: INSERT dispute status=1 (举证中)
    BE->>R: ZADD delay:dispute:evidence 48h
    BE-->>B: 已发起仲裁
    BE->>S: 通知讲师上传证据

    alt 买卖双方协商成功
        B->>BE: POST /api/order/refund/negotiate agree 50%
        S->>BE: POST /api/order/refund/negotiate agree 50%
        BE->>PS: 调用退款接口（后续接入）
        BE->>DB: INSERT refund_record
        BE->>DB: UPDATE order.status=80
    else 48h 未达成一致 → 平台介入
        BE->>AD: 推送待仲裁列表
        AD->>AD: 3人仲裁团查阅证据
        AD->>BE: POST /admin/dispute/resolve {resultType, refundAmount}
        BE->>PS: 调用退款接口（后续接入）
        alt 全额退 or 部分退
            BE->>DB: UPDATE order.status=80
            BE->>BE: 扣减卖家冻结余额（若已入账）
        else 驳回退款
            BE->>DB: UPDATE order.status=50
            BE->>BE: 正常结算讲师
        end
    end
```

```mermaid
flowchart TD
```

## 11. 流程八：评价与信誉

```mermaid
sequenceDiagram
    participant B as 买家
    participant BE as 后端
    participant DB as MySQL

    B->>BE: POST /api/review/submit (score, tags, content)
    BE->>DB: 校验 order.status=50 且未评价
    BE->>BE: riskService.checkText(content)
    BE->>DB: INSERT review
    BE->>DB: UPDATE service_item.score_avg (重新计算)
    BE->>BE: 计算信誉分变动
    BE->>DB: UPDATE user.credit_score += delta
    BE->>DB: INSERT credit_log
    alt credit_score < 80
        BE->>DB: 标记该讲师搜索降权
    else credit_score < 60
        BE->>DB: 下架该讲师所有服务
    end
    BE-->>B: OK
```

**信誉分算法**：

```java
int delta = switch (score) {
    case 5 -> +2;
    case 4 -> +1;
    case 3 ->  0;
    case 2 -> -3;
    case 1 -> -5;
    default -> 0;
};
if (disputeLose) delta -= 10;
if (timeoutCancel) delta -= 2;
```

| 阈值 | 效果 |
| :--- | :--- |
| ≥ 110 | "优质讲师" 徽章 |
| 80 ~ 109 | 正常 |
| 60 ~ 79 | 搜索降权 |
| < 60 | 禁止发布新服务，已上架服务下架 |

## 13. 关键异常路径汇总

| 场景 | 处理 | 补偿方式 |
| :--- | :--- | :--- |
| 支付回调超时 | 微信会重试 6 次（最长 24h） | 幂等 + 对账定时任务 |
| 退款接口失败 | `refund_record.status=3`，运营介入 | 人工重试，每日对账 |
| OCR 服务不可用 | 转人工审核队列 | 运营手工处理 |
| Redis 宕机 | 延迟任务丢失 | DB `expire_time` 兜底扫描 |
| MySQL 主从延迟 | 写后读不一致 | 关键路径强制读主 |
| 订单状态并发 | 两个请求同时更新 | UPDATE 带 `WHERE status=from` |

## 14. 幂等性设计汇总

| 场景 | 幂等键 | 机制 |
| :--- | :--- | :--- |
| 用户下单 | `X-Idempotency-Key`（UUID） | Redis SETNX 5min |
| 支付回调 | `out_trade_no` | DB 唯一索引 + 状态校验 |
| 退款调用 | `refund_no` | DB 唯一索引 + 状态校验 |
| 接单/确认 | `orderId + targetStatus` | UPDATE 带 `WHERE status=from` |
| 提现申请 | `withdraw_no` | DB 唯一索引 |
| 评价提交 | `orderId + reviewType` | DB `uk_order_reviewer` |
